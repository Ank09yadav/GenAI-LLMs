## 81. How do you handle rate limits, timeouts, and retries?

### Answer

In distributed AI systems, network instability, server saturation, and API quota limits are not rare anomalies; they are **expected steady-state operating conditions**.

Commercial LLM providers enforce strict dual-axis quotas: **Requests Per Minute (RPM)** and **Tokens Per Minute (TPM)**. When traffic surges, APIs return `HTTP 429 Too Many Requests`, while GPU cluster saturation triggers `HTTP 504 Gateway Timeouts` and `HTTP 503 Service Unavailable`.

Handling these failures gracefully requires combining **Exponential Backoff with Full Jitter**, **Client-Side Token Buckets**, and **Circuit Breakers**.

```text
                           The Thundering Herd vs. Jitter Backoff
                           
 Naive Retries (The "Thundering Herd" Catastrophe):
 100 requests hit 429 Rate Limit ──► All wait exactly 1.0s ──► All 100 retry at once!
 Result: Immediate secondary 429 crash! The API never recovers!
 
 Exponential Backoff with Full Jitter (De-synchronized Smooth Recovery):
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ Request 1:  Wait Random(0, 2^1) = 0.4s  ──► Retries smoothly at t = 0.4s    │
 │ Request 2:  Wait Random(0, 2^1) = 1.8s  ──► Retries smoothly at t = 1.8s    │
 │ Request 3:  Wait Random(0, 2^1) = 1.1s  ──► Retries smoothly at t = 1.1s    │
 └─────────────────────────────────────────────────────────────────────────────┘
 Result: Retries are mathematically dispersed across time, allowing API queues to clear!
```

---

### Strategy 1: Exponential Backoff with Full Jitter

A naive exponential backoff algorithm multiplies wait time by a power of 2 ($t = t_{\text{base}} \times 2^{\text{attempt}}$). However, if hundreds of concurrent workers fail simultaneously, static backoff simply pushes the collision point further out in time.

The mathematically proven solution (pioneered by AWS Architecture) is **Full Jitter**:

$$t_{\text{sleep}} = \text{UniformRandom}\left(0, \, \min\left(t_{\text{max}}, \, t_{\text{base}} \cdot 2^{\text{attempt}}\right)\right)$$

Where:
- $t_{\text{base}}$: Base backoff time (typically $0.5\text{s}$ or $1.0\text{s}$).
- $t_{\text{max}}$: Upper cap on backoff delay (typically $16\text{s}$ or $32\text{s}$).
- $\text{UniformRandom}$: Selects a random floating-point scalar between $0$ and the exponential ceiling, completely breaking synchronization between competing threads.

---

### Strategy 2: Client-Side Proactive Rate Limiting (Token Bucket in Redis)

Rather than passively waiting for the LLM vendor to reject calls with HTTP 429, enterprise gateways enforce **Client-Side Token Bucket Rate Limiting** using distributed Redis:

```text
 Inbound User Request (Estimated: 2,000 tokens)
                    │
                    ▼
 ┌────────────────────────────────────────────────────────┐
 │ Distributed Redis Token Bucket                         │
 │ - Capacity: 100,000 TPM                                │
 │ - Refill Rate: 1,666 tokens / sec                      │
 └──────────────────┬─────────────────────────────────────┘
                    │
       ┌────────────┴────────────┐
       ▼ Has 2,000 tokens?       ▼ Out of Tokens?
 [Deduct 2,000 & Dispatch]    [Hold in Celery/SQS Queue]
                              [Wait for token refill]
```

- **Proactive Throttling:** Requests are queued before departure, ensuring the organization never breaches its external contractual API limits.
- **Provider Headers:** Inspect incoming HTTP response headers (`x-ratelimit-remaining-tokens`, `retry-after`) and dynamically calibrate the client-side refill rate.

---

### Strategy 3: The Circuit Breaker Pattern

If a provider undergoes an extended outage, repeatedly attempting retries with backoff wastes time and blocks worker threads. The **Circuit Breaker** (Netflix Hystrix pattern) automates failover:

```text
 ┌──────────────┐         Consecutive Failures > Threshold         ┌──────────────┐
 │    CLOSED    │ ───────────────────────────────────────────────► │     OPEN     │
 │ Normal Ops   │                                                  │ Failover Now │
 └──────────────┘                                                  └──────────────┘
        ▲                                                                 │
        │                        Cooldown Expired (e.g., 60s)             │
        └───────────────── ┌─────────────────┐ ◄──────────────────────────┘
           Canary Passes   │    HALF-OPEN    │
                           │ Send 1 Canary Req│
                           └─────────────────┘
```

1. **Closed (Normal):** Requests flow to primary model.
2. **Open (Tripped):** If the failure rate exceeds $50\%$ over a 30-second window, the circuit trips to **Open**. All future requests instantly bypass the primary model and route to the **secondary fallback model** without attempting a single call to the primary.
3. **Half-Open (Canary Testing):** After a 60-second cooldown, the breaker allows a single canary request to test the primary provider. If successful, the circuit resets to **Closed**; if it fails, it trips back to **Open**.

### Production Implementation Using Tenacity

In Python microservices, retries must be restricted strictly to **transient, retryable errors** (never retry deterministic HTTP 400 Bad Request or 401 Unauthorized!):

```python
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception
import httpx
from openai import OpenAI, RateLimitError, APIConnectionError, InternalServerError

# Define which exceptions are safe to retry
def is_retryable_error(exception: Exception) -> bool:
    return isinstance(exception, (RateLimitError, APIConnectionError, InternalServerError))

client = OpenAI()

@retry(
    retry=retry_if_exception(is_retryable_error),
    wait=wait_random_exponential(multiplier=1.0, max=20.0), # Exponential backoff with Full Jitter
    stop=stop_after_attempt(4), # Max 4 attempts before raising exception
    reraise=True
)
def call_llm_with_resilience(prompt: str) -> str:
    try:
        response = client.chat.completions.create(
            model="gpt-4o",
            messages=[{"role": "user", "content": prompt}],
            timeout=10.0 # Strict 10-second timeout to prevent thread hanging
        )
        return response.choices[0].message.content
    except Exception as e:
        print(f"Encountered retryable error: {e}. Backing off with jitter...")
        raise e
```

### Key Point

> **Production resilience requires handling rate limits and timeouts through Exponential Backoff with Full Jitter to eliminate thundering-herd collisions, client-side Token Bucket queues in Redis to prevent 429s, and Circuit Breakers to failover instantly during prolonged vendor outages.**

---

### Interview Answer

> "Handling rate limits and timeouts in enterprise LLM systems requires a layered resilience framework:
> 1. **Exponential Backoff with Full Jitter:** When encountering transient HTTP 429 or 503 errors, retrying with static intervals causes the 'thundering herd' problem where concurrent requests collide repeatedly. Full jitter randomizes the sleep interval between zero and the exponential ceiling, desynchronizing retries across worker pools.
> 2. **Targeted Exception Filtering:** Using libraries like `tenacity`, we strictly whitelist retryable errors (RateLimitError, APIConnectionError, 5xx server errors) while immediately failing fast on deterministic client errors (HTTP 400 Bad Request or schema invalidity).
> 3. **Proactive Client-Side Token Buckets:** We track token consumption in a centralized Redis token bucket to throttle or queue requests before they breach vendor limits.
> 4. **Circuit Breakers:** If an endpoint's failure rate exceeds a threshold (e.g., 50% over 30s), the circuit opens, immediately routing traffic to a secondary fallback provider without wasting retry latency."
