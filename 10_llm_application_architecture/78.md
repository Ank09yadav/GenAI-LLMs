## 78. How do you reduce latency in LLM systems?

### Answer

Reducing latency in Large Language Model applications requires targeting the two distinct physical bottlenecks that govern text generation: **Time to First Token (TTFT)**, which is dominated by the compute-bound prefill phase, and **Inter-Token Latency (ITL)**, which is dominated by the memory-bandwidth-bound decode phase.

$$\text{Total End-to-End Latency} = \text{TTFT} + (N_{\text{output\_tokens}} - 1) \times \text{ITL} + \text{Network Overhead}$$

To achieve sub-second response times, engineering teams apply optimizations across the **model architecture**, **serving engine**, and **application workflow**.

```text
                           The Latency Reduction Playbook
                           
 ┌──────────────────────────────────────┐      ┌──────────────────────────────────────┐
 │ TARGETING TTFT (Prefill Phase)       │      │ TARGETING ITL (Decode Phase)         │
 ├──────────────────────────────────────┤      ├──────────────────────────────────────┤
 │ 1. Prompt / Prefix Caching           │      │ 1. Speculative Decoding (EAGLE)      │
 │ 2. Context Pruning (LLMLingua)       │      │ 2. Weight Quantization (FP8 / INT4)  │
 │ 3. Chunked Prefill Scheduling        │      │ 3. Grouped-Query Attention (GQA)     │
 └──────────────────────────────────────┘      └──────────────────────────────────────┘
                    ▲                                             ▲
                    │                                             │
 ┌──────────────────┴─────────────────────────────────────────────┴───────────────────┐
 │ APPLICATION & SYSTEM ARCHITECTURE LAYER                                            │
 │ - Semantic Caching (Redis: < 30ms instant response)                                │
 │ - Intelligent Model Tiering (Routing simple queries to Claude 3.5 Haiku)           │
 │ - Parallel Tool Execution (asyncio.gather for multi-tool calling)                  │
 └────────────────────────────────────────────────────────────────────────────────────┘
```

### 1. Optimizing Time to First Token (TTFT)

#### A. Prompt / Prefix Caching (The Single Biggest TTFT Saver)
- **The Mechanism:** Frontier APIs (Anthropic, OpenAI) and local serving engines (vLLM) automatically cache the KV representations of prompt prefixes.
- **The Impact:** When a user submits a query with a shared 2,000-token system prompt and few-shot examples, the engine **completely skips the prefill calculation for the cached tokens**!
- **Result:** Slashes TTFT from $1,200\text{ms}$ down to **$< 200\text{ms}$** ($6\times$ acceleration) while slashing API costs by up to $80\%$.

#### B. Context Pruning & Compression (LLMLingua)
- Passing 30 retrieved RAG chunks directly into the prompt inflates prefill latency.
- Utilizing prompt compression engines like **LLMLingua** discards syntactically redundant words using token perplexity scores, compressing contexts by **$3\times - 5\times$** without sacrificing reasoning accuracy.

#### C. Chunked Prefill (vLLM & TensorRT-LLM)
- Large prompt prefills (e.g., an 8,000-token document) monopolize GPU Tensor Cores, starving concurrent decode requests and causing erratic latency spikes.
- **Chunked Prefill** splits large prompts into smaller 512-token chunks, co-scheduling them alongside active decode iterations to maintain consistent, smooth token streaming across all users.

---

### 2. Optimizing Inter-Token Latency (ITL / Generation Speed)

#### A. Speculative Decoding (EAGLE / Medusa)
- **The Core Problem:** Decoding is memory-bound; loading 70B parameters yields only 1 token per memory fetch.
- **The Solution:** A small, fast "Draft Model" (e.g., LLaMA-3-1B) speculatively guesses $K = 5$ candidate tokens at blazing speed. The large "Target Model" (LLaMA-3-70B) evaluates all 5 tokens **in a single parallel forward pass (GEMM)**!
- **The Math:** If the target model accepts 4 out of 5 tokens, you generate 4 tokens for the memory bandwidth cost of a single forward pass!
- **Result:** Increases generation throughput by **$2\times \text{ to } 3\times$** with **zero loss in mathematical output quality**.

```text
 Speculative Decoding Loop:
 1. Draft Model (1B):   Drafts: ["The", "economy", "expanded", "by", "two"] (Fast!)
 2. Target Model (70B): Verifies all 5 tokens concurrently in ONE forward pass.
 3. Result: 4 tokens accepted simultaneously! Latency drops by 65%!
```

#### B. Weight Quantization (W4A16 & FP8)
- Quantizing 16-bit weights to 8-bit FP8 or 4-bit INT4 cuts memory traffic in half or quarters.
- Because decoding is memory-bandwidth bound, halving the memory bytes loaded per token directly **doubles the tokens-per-second generation speed**.

---

### 3. Application-Level Architectural Optimizations

| Technique | Description | Latency Impact |
| :--- | :--- | :--- |
| **Semantic Caching** | Storing prior query/answer pairs in a Redis vector cache; returns results on cosine match $\ge 0.98$. | Slashes latency from $3,000\text{ms} \to \mathbf{25\text{ms}}$ |
| **Model Tier Cascades** | Directing simple extraction and categorization queries to ultra-fast models (Haiku / 4o-mini). | Cuts end-to-end latency by $60\% - 75\%$ |
| **Parallel Tool Execution** | Dispatching independent external API calls concurrently using `asyncio.gather()` rather than in serial. | Replaces cumulative latency ($\sum t_i$) with maximum latency ($\max t_i$). |

---

### Key Point

> **Reducing LLM latency requires targeting both TTFT and ITL. TTFT is slashed via prompt prefix caching, context pruning, and chunked prefill; ITL is accelerated via speculative decoding (yielding $2\times - 3\times$ speedups), FP8/INT4 weight quantization, and semantic caching.**

### Interview Answer

> "Reducing latency in production LLMs requires decomposing total latency into its two physical constituents: **Time to First Token (TTFT)** during prefill and **Inter-Token Latency (ITL)** during decode:
> 
> 1. **To reduce TTFT (prefill):** We implement **prompt/prefix caching** to reuse precomputed KV states for static system instructions and few-shot exemplars, which slashes prefill latency by over 80%. We also employ context pruning tools like LLMLingua and enable chunked prefills in our serving engine to prevent massive prompts from starving active decode batches.
> 2. **To reduce ITL (decode):** Because decoding is memory-bandwidth bound, we deploy **speculative decoding** (using a lightweight draft model verified in parallel by the target model, yielding a $2\times$ to $3\times$ throughput speedup) and leverage **FP8/INT4 weight quantization** to halve memory bus traffic.
> 3. **At the system tier:** We implement **semantic caching (Redis)** to serve frequent queries in under 30ms, and execute independent agent tool calls concurrently via `asyncio.gather()`."
