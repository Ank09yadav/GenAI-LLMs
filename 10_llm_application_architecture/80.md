## 80. How do you implement fallback and routing strategies?

### Answer

In enterprise software engineering, relying on a single commercial AI provider creates a **Single Point of Failure (SPOF)**. Cloud LLM providers regularly experience degraded performance, sudden latency spikes, regional networking partitions, and aggressive rate limits (HTTP 429).

A production-grade architecture must implement **Intelligent Model Routing** and **Automated Fallback Cascades** to decouple the application from individual vendors, guaranteeing **99.99% uptime** and minimizing serving costs.

```text
                           The Enterprise Routing & Fallback Gateway
                           
                                     Incoming User Request
                                               │
                                               ▼
                              ┌─────────────────────────────────┐
                              │ LLM GATEWAY (LiteLLM / Portkey) │
                              └────────────────┬────────────────┘
                                               │
               ┌───────────────────────────────┴───────────────────────────────┐
               ▼                                                               ▼
 ┌───────────────────────────┐                                   ┌───────────────────────────┐
 │ STRATEGY 1: Intent Router │                                   │ STRATEGY 2: Failover Chain│
 │ Complexity Classifier:    │                                   │ Primary: OpenAI GPT-4o    │
 │ - Simple ──► GPT-4o-mini  │                                   │    │ (Fails on 429 / 503) │
 │ - Complex ─► Claude 3.5   │                                   │    ▼                      │
 └───────────────────────────┘                                   │ Secondary: Azure GPT-4o   │
                                                                 │    │ (Fails on Timeout)   │
```

### The Four Primary Routing Paradigms

```text
 ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
 │ 1. Failover / Resilience Cascades                                                           │
 │ If Endpoint A encounters an error (HTTP 429, 500, 503, timeout), immediately and invisibly  │
 │ re-dispatch the exact prompt payload to Endpoint B with zero downtime.                      │
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 2. Complexity & Cost Routing (Model Tiering)                                                │
 │ A fast, local classifier analyzes query semantic entropy and routes to small or large models│
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 3. Load Balancing Across Keys & Regions                                                     │
 │ Distributes high-throughput traffic round-robin across multiple API keys, regions (US-East, │
 │ EU-West), or cloud accounts to multiply total effective TPM/RPM rate limits.               │
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 4. Hedged Requests (Speculative Racing)                                                     │
 │ If a primary provider's TTFT exceeds 1.5 seconds, automatically fire a duplicate request to  │
 │ a secondary provider and cancel the slower connection as soon as the first token arrives!  │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Production Implementation with LiteLLM

Using an open-source model gateway like **LiteLLM**, developers can configure automated fallback cascades and load balancing in Python with standard OpenAI-compatible interfaces:

```python
from litellm import Router

# Define the Resilient Fallback Model List
model_list = [
    {
        "model_name": "production-llm",
        "litellm_params": {
            "model": "openai/gpt-4o",
            "api_key": "sk-openai-primary...",
            "api_base": "https://api.openai.com/v1"
        }
    },
    {
        "model_name": "production-llm",
        "litellm_params": {
            "model": "azure/gpt-4o",
            "api_key": "azure-key...",
            "api_base": "https://company-eastus.openai.azure.com/"
        }
    },
    {
        "model_name": "production-llm",
        "litellm_params": {
            "model": "anthropic/claude-3-5-sonnet-20241022",
            "api_key": "sk-ant-..."
        }
    }
]

# Initialize Router with Exponential Backoff and Circuit Breaker
router = Router(
    model_list=model_list,
    fallbacks=[{"production-llm": ["azure/gpt-4o", "anthropic/claude-3-5-sonnet-20241022"]}],
    num_retries=3,
    timeout=5.0, # Failover if no response within 5 seconds
    allowed_fails=2,
    cooldown_time=60 # Trip circuit breaker for 60 seconds if 2 failures occur
)

async def execute_resilient_completion(prompt: str):
    # The application calls "production-llm" generically.
    # The router handles load balancing, health checks, and failovers automatically!
    response = await router.acompletion(
        model="production-llm",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.2
    )
    return response.choices[0].message.content
```

### Complexity-Based Semantic Routing Architecture

How do you determine whether a query is "simple" or "complex" in under $10\text{ms}$?

```text
 User Query
     │
     ▼
 ┌────────────────────────────────────────────────────────┐
 │ Embedding Vector + Lightweight Logistic Classifier     │  ◄── Evaluated in < 5ms!
 └──────────────────────────┬─────────────────────────────┘
                            │
             ┌──────────────┴──────────────┐
             ▼ Score < 0.6                 ▼ Score >= 0.6
 ┌──────────────────────────┐  ┌──────────────────────────┐
 │ Low-Complexity Query     │  │ High-Complexity Query    │
 │ (Factual, Triage, Sum)   │  │ (Code, Legal, Proofs)    │
 │ Route: GPT-4o-mini       │  │ Route: GPT-4o / Sonnet   │
 │ Cost: $0.15 / MTok       │  │ Cost: $3.00 / MTok       │
 └──────────────────────────┘  └──────────────────────────┘
```

1. **Embedding Distance to Exemplars:** Compute cosine similarity against cluster centroids of known easy vs. hard tasks.
2. **Structural Heuristics:** Queries demanding strict code generation, mathematical proofs, or multi-hop logic are tagged for frontier routing; basic FAQ extraction is routed to lightweight tiers.

### Key Point

> **Production systems eliminate vendor lock-in and downtime through AI Gateway routing. Fallback cascades automatically divert traffic from primary models to secondary cloud regions or alternative providers upon encountering 429/503 errors, while intent classifiers route queries dynamically by complexity to slash costs.**

### Interview Answer

> "Implementing fallback and routing strategies in production requires decoupling application logic from concrete model providers using an AI Gateway like LiteLLM or Portkey.
> 
> We implement routing across two primary vectors:
> 1. **Resilience & Failover Cascades:** To guarantee high availability, requests follow a prioritized fallback chain: for example, failing over from direct OpenAI to Azure-hosted OpenAI, then to Anthropic Claude 3.5 Sonnet, and finally to an internal self-hosted vLLM cluster. The gateway manages timeouts, retries, and circuit breakers with cooldown periods.
> 2. **Economic Complexity Routing:** We deploy a sub-10ms semantic intent classifier to triage incoming prompts. Roughly 75% of straightforward extraction and summarization queries are routed to cost-effective models like GPT-4o-mini or Claude 3.5 Haiku, reserving expensive frontier reasoning models exclusively for complex coding or logical workflows."
