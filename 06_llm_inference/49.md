## 49. What is the KV cache?

### Answer

The **Key-Value (KV) Cache** is the foundational algorithmic optimization that makes autoregressive Transformer inference viable in production. 

During text generation, each new token must attend to all previous tokens in the sequence. Without a KV cache, the model would be forced to recompute the **Key** and **Value** projection vectors for all historical tokens from scratch at every single generation step, causing computational latency to explode from $O(T)$ to $O(T^2)$ per token ($O(T^3)$ total sequence complexity).

By caching past Key and Value vectors directly in GPU High Bandwidth Memory (VRAM), the model computes projections **only for the single active token** at step $t$.

```text
                     Attention Computation With vs. Without KV Cache
                     
 WITHOUT KV Cache (Disastrous O(T^2) Recomputation at Step t):
 Input: [Tok 1, Tok 2, Tok 3, ..., Tok t]
 Re-embed all t tokens ──► Re-project Q, K, V for all t tokens across all L layers!
 
 WITH KV Cache (O(1) Incremental Computation at Step t):
 Input: [Tok t only]
 Compute: q_t, k_t, v_t for the single new token
 ┌────────────────────────────────────────────────────────┐
 │ Cached Keys:   [k_1, k_2, k_3, ..., k_{t-1}] + k_t     │
 │ Cached Values: [v_1, v_2, v_3, ..., v_{t-1}] + v_t     │
 └────────────────────────┬───────────────────────────────┘
                          │
                          ▼
 Attention Score = softmax(q_t · [K_cached]^T / √d) · [V_cached]
```

---

### Mathematical Memory Footprint Formula

While the KV cache dramatically slashes compute time, it introduces a severe **memory consumption bottleneck**. The memory occupied by the KV cache across all layers and batches is:

$$\text{Memory}_{\text{KVCache}} = 2 \times 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times L \times B \quad \text{bytes}$$

Where:
- First factor of $2$: Storing both **Keys** and **Values**.
- Second factor of $2$: **16-bit floating-point precision** (FP16 or BF16 = 2 bytes per float).
- $n_{\text{layers}}$: Total number of Transformer decoder layers.
- $n_{\text{kv\_heads}}$: Number of Key/Value attention heads (e.g., in Multi-Query or Grouped-Query Attention).
- $d_{\text{head}}$: Dimension of each attention head ($d_{\text{model}} / n_{\text{heads}}$).
- $L$: Sequence length (Prompt tokens + Generated tokens).
- $B$: Concurrent batch size.

---

### Concrete Real-World Calculation: LLaMA-2-70B

Let's calculate the KV cache requirement for **LLaMA-2-70B** using Multi-Head Attention (MHA):
- $n_{\text{layers}} = 80$
- $n_{\text{kv\_heads}} = 64$
- $d_{\text{head}} = 128$
- Sequence length $L = 4,096$ tokens

$$\text{Memory per single sequence } (B=1):$$
$$4 \times 80 \times 64 \times 128 \times 4,096 \approx 10,737,418,240 \text{ bytes} \approx \mathbf{10.74\text{ GB}}$$

- For a **single user**, the KV cache alone demands $\approx 10.7\text{ GB}$ of VRAM.
- For a modest batch size of $B = 16$ concurrent users:
  $$16 \times 10.74\text{ GB} = \mathbf{171.8\text{ GB of VRAM!}}$$
This exceeds the total memory of two entire NVIDIA A100 (80GB) GPUs **just to hold intermediate attention vectors**, before accounting for model weights!

### Architectural Solutions to the KV Cache Memory Crisis

```text
 ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
 │ 1. Grouped-Query Attention (GQA - LLaMA-3, Mistral)                                         │
 │ Shares a single Key-Value head across 8 Query heads, immediately slashing KV cache by 87.5%!│
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 2. PagedAttention (vLLM Engine)                                                             │
 │ Solves physical memory fragmentation by allocating KV cache in non-contiguous virtual pages │
 │ (like OS virtual memory), boosting GPU serving capacity by 2x to 4x.                        │
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 3. KV Cache Quantization (FP8 / INT4)                                                       │
 │ Stores cached Keys and Values in 8-bit or 4-bit precision instead of FP16, saving 50-75%   │
 │ memory with negligible perplexity degradation.                                              │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

---

### Key Point

> **The KV cache stores the Key and Value projection vectors of preceding tokens across all Transformer layers. This avoids $O(T^2)$ recomputation at each autoregressive step, transforming per-token inference complexity from quadratic to linear, at the expense of substantial GPU VRAM consumption.**

---

### Interview Answer

> "The KV cache is a vital inference optimization for autoregressive Transformers. Because each newly generated token must attend to all previous tokens, generating token $t$ naively requires re-running self-attention over all $t-1$ historical tokens from scratch, resulting in $O(T^2)$ compute per token. 
> 
> The KV cache solves this by persisting past Key and Value vectors in GPU memory (HBM). At step $t$, the model projects $Q, K, V$ for only the single new token, appends $K_t$ and $V_t$ to the cache, and computes attention against the cached history. 
> 
> However, KV cache memory scales linearly with sequence length, batch size, and layer count according to $4 \cdot n_{\text{layers}} \cdot n_{\text{kv\_heads}} \cdot d_{\text{head}} \cdot L \cdot B$ bytes. In large models like LLaMA-2-70B, this consumes tens of gigabytes of VRAM, which modern architectures mitigate using Grouped-Query Attention (GQA), PagedAttention (vLLM), and FP8 KV quantization."
