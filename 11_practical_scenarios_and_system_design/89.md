## 89. System Design: Design an internal code review assistant at scale.

### Answer

Designing an enterprise **Automated Code Review Assistant** for 10,000+ software engineers handling **50,000 daily Pull Requests (PRs)** requires solving three severe engineering challenges:
1. **The Context Boundary Problem:** A git diff touches a few lines of code, but reviewing it accurately requires understanding external functions, class definitions, and dependencies across the entire repository.
2. **The Developer Alert Fatigue Problem:** If the assistant posts trivial linter warnings or hallucinated nitpicks, developers will ignore or disable it. The system must maintain a **false-positive rate $< 5\%$**.
3. **The Data Privacy Constraint:** Proprietary enterprise source code must never leak to public commercial model endpoints.

### Step-by-Step Architecture Deep Dive

#### Stage 1: Fast Static Pre-Filtering (Saving 70% of LLM Compute)
A critical design mistake is asking an LLM to check indentation, naming conventions, or missing semicolons. 
- Fast deterministic linters (**Ruff**, **ESLint**, **Semgrep**) evaluate the PR diff in $<2\text{ seconds}$.
- If a flaw is caught statically, it is flagged immediately without triggering the LLM tier, saving hundreds of thousands of dollars in GPU inference!

#### Stage 2: Resolving Repository Context via Code Graphs (SCIP / Tree-sitter)
When a developer modifies line 42 in `auth.py`:
```python
# Diff:
- user = get_user(user_id)
+ user = get_user_cached(user_id)
```
The LLM cannot evaluate this change without knowing how `get_user_cached` is implemented:
1. **Tree-sitter Parsing:** Parses the diff into an **Abstract Syntax Tree (AST)** to extract modified function names and signatures.
2. **SCIP / LSIF Symbol Indexing:** Looks up the definition of `get_user_cached` and its return types across the repository's pre-indexed symbol graph.
3. **Context Injection:** Injects the relevant class definition into the prompt context alongside the diff!

#### Stage 3: Prompt Construction & Review Focus Areas
The review engine focuses strictly on **high-cognitive architectural and security flaws**:
- **Concurrency & Race Conditions:** Missing database locks, deadlocks in async threads.
- **Security Vulnerabilities:** SQL injection vectors, unvalidated deserialization, SSRF risks, hardcoded API secrets.
- **Resource Leaks:** Unclosed database connections, unhandled exceptions in background workers.

```xml
<context>
File: services/auth.py
Symbol Definitions:
def get_user_cached(user_id: str) -> Optional[User]: ...
</context>

<diff>
{git_diff_chunk}
</diff>

<instructions>
1. Identify high-severity logic bugs, concurrency flaws, or security vulnerabilities introduced in the diff.
2. Ignore minor formatting, whitespace, or stylistic preferences.
3. For each valid issue, output:
   - File Path & Exact Line Number
   - Severity: HIGH | MEDIUM
   - Confidence Score: 0.0 to 1.0
   - Explanation & Concrete Code Fix Diff
</instructions>
```

#### Stage 4: Confidence Gating & Spam Suppression (Preventing Fatigue)
Developer trust is destroyed if the bot posts noisy comments:
- Every suggested review item must return a typed Pydantic object containing a `confidence_score: float`.
- **The Filter Rule:**
  $$\text{If } \text{confidence\_score} < 0.85 \lor \text{severity} == \text{"LOW"} \implies \mathbf{DISCARD}$$
- Only comments with overwhelming model certainty and high impact are posted inline directly to the GitHub PR.

### Key Point

> **An enterprise code review assistant at scale combines static analysis (Semgrep) to catch trivial syntax without LLM compute, SCIP/Tree-sitter code graphs to resolve cross-file repository context, a private GPU cluster (vLLM) to protect code confidentiality, and a strict confidence threshold ($>0.85$) to eliminate developer alert fatigue.**

### Interview Answer

> "Designing an enterprise code review assistant for 50,000 daily PRs requires solving three key architectural challenges:
> 1. **Compute Efficiency via Hybrid Pipeline:** We never use LLMs for formatting or syntax errors. Inbound webhooks pass through Kafka into a fast static analysis layer (Semgrep, Ruff) that catches linting issues in seconds. Only complex diffs proceed to the LLM tier.
> 2. **Cross-File Repository Context:** To understand dependencies beyond the isolated diff, we use Tree-sitter to parse the AST and query a repository symbol graph (using SCIP/LSIF) to pull external class definitions and caller signatures into the prompt context.
> 3. **Eliminating Alert Fatigue:** Developer adoption collapses if the bot posts false positives. We enforce structured Pydantic outputs with explicit confidence scores and filter out any comment with confidence $<0.85$ or low severity.
> 4. **Privacy & Security:** Because corporate IP is paramount, the LLM cluster runs open-weights models (like DeepSeek-Coder or LLaMA-3-70B) self-hosted on private vLLM clusters inside our isolated cloud VPC with zero external data egress."
