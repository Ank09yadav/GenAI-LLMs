## 87. Scenario: How do you decide between Prompting, Fine-Tuning, and RAG for a new project?

### Answer

Selecting the wrong architecture at the inception of an enterprise AI initiative is one of the most expensive engineering mistakes a team can make. 

A common anti-pattern is jumping immediately to **Fine-Tuning** in an attempt to "teach" an LLM internal corporate documents—a strategy doomed to failure because parametric neural weights are lossy statistical approximations, not queryable databases.

To make the optimal architectural decision, engineers evaluate the project through a **4-Question Diagnostic Decision Framework**.

```text
                           The Architectural Decision Tree
                           
 Start: New Generative AI Project
                   │
                   ▼
 [Question 1: Does the system require dynamic, private, or real-time factual knowledge?]
                   │
         ┌─────────┴─────────┐
         ▼ YES               ▼ NO
 ┌─────────────────┐   [Question 2: Does the task require specialized formatting, custom DSLs,
 │  RAG REQUIRED   │    or radical style consistency that prompting cannot reliably enforce?]
 └────────┬────────┘         │
          │                  │
          │        ┌─────────┴─────────┐
          │        ▼ YES               ▼ NO
          │  ┌─────────────────┐   [Question 3: Are prompt tokens causing excessive latency/cost?]
          │  │FINE-TUNING (LoRA│         │
          │  └────────┬────────┘         │
          │           │        ┌─────────┴─────────┐
          │           │        ▼ YES               ▼ NO
          │           │  ┌─────────────────┐ ┌─────────────────────────┐
          │           │  │FINE-TUNING (SFT)│ │   PROMPT ENGINEERING    │
          │           │  └─────────────────┘ │ (Few-Shot / XML Schema) │
          ▼           ▼                      └─────────────────────────┘
  ┌────────────────────────────────────────┐
  │     HYBRID: RAG + FINE-TUNING          │
  │ (Domain Style via LoRA + Facts via RAG)│
  └────────────────────────────────────────┘
```

---

### The 4 Core Diagnostic Questions

#### Question 1: Is Dynamic, Verifiable External Knowledge Required?
- **Indicator:** The application must answer questions based on company policies, customer account balances, code repositories, or real-time news.
- **Decision:** **RAG (Retrieval-Augmented Generation) is non-negotiable.**
  - LLM weights cannot store live facts. Fine-tuning to memorize facts leads to ungrounded hallucinations, offers zero source citations, and requires expensive re-training whenever a document updates.

#### Question 2: Is the Task Demanding Specialized Formatting or Custom DSLs?
- **Indicator:** The output must conform to an obscure internal query language, proprietary binary syntax, or an intricate 50-field JSON schema that base models fail to generate even with few-shot prompting.
- **Decision:** **Fine-Tuning (LoRA / SFT) is required.**
  - Fine-tuning adjusts the model's output distribution to internalize custom syntax and grammar directly into its weights.

#### Question 3: Is Prompt Token Overhead Creating a Cost or Latency Bottleneck?
- **Indicator:** The system requires 2,500 tokens of complex instructions, guidelines, and few-shot examples on **every single user request**, causing high API bills ($10K+/month) and sluggish TTFT ($>2$ seconds).
- **Decision:** **Fine-Tuning (Model Distillation) is justified.**
  - By fine-tuning a small 8B model on golden prompt-completion pairs, the 2,500 tokens of prompt rules are internalized into model weights. User queries shrink to 50 tokens, cutting latency and API costs by **$>80\%$**.

#### Question 4: Can the Problem be Solved with In-Context Learning Alone?
- **Indicator:** The task involves general summarization, translation, common entity extraction, or conversational Q&A without proprietary syntax.
- **Decision:** **Prompt Engineering is the optimal solution.**
  - Instant deployment, zero GPU training costs, zero dataset preparation overhead, and zero risk of catastrophic forgetting.

### Archetypal Enterprise Case Studies

| Project Archetype | Optimal Architecture | Architectural Rationale |
| :--- | :--- | :--- |
| **Enterprise HR Helpdesk Bot** | **RAG + Prompt Engineering** | Company HR policies update frequently and require direct source citations and user-level ACL access control. |
| **COBOL-to-Java Code Migration Tool**| **Fine-Tuning (LoRA)** | Base models are weak on legacy proprietary COBOL dialects. Fine-tuning internalizes syntax mappings without needing external retrieval. |
| **Clinical Diagnostic Assistant** | **RAG + Fine-Tuning (Hybrid)** | Fine-tuning internalizes clinical medical terminology and SOAP note formatting; RAG retrieves the patient's active medical history and live FDA alerts. |
| **Customer Feedback Sentiment Triage**| **Prompt Engineering** | Pure zero-shot or few-shot classification using standard LLMs easily solves sentiment analysis with zero training overhead. |

### The Recommended Evolutionary Workflow

In production engineering, the golden rule is: **Always start simple and graduate as constraints demand**:

```text
 Stage 1: PROMPT ENGINEERING (Ship MVP in 2 days)
 └─► Build robust prompt with few-shot exemplars and Pydantic schemas.
     │
     ▼ (If model lacks real-time facts or company data)
 Stage 2: ADD RAG (Retrieval-Augmented Generation)
 └─► Index documents in a vector DB; ground answers in verified context.
     │
     ▼ (If prompt tokens are too costly, latency is too high, or formatting drifts)
 Stage 3: ADD FINE-TUNING (LoRA / Distillation)
 └─► Distill task logic into an 8B model; combine with RAG for live facts.
```

---

### Key Point

> **Choose RAG when dynamic facts, external documents, or citations are required; choose Fine-Tuning when specialized syntax, custom formatting, or prompt token amortization is required; choose Prompt Engineering for rapid iteration without training compute. The optimal enterprise pattern is evolutionary: start with prompting, augment with RAG, and specialize via fine-tuning.**

### Interview Answer

> "When deciding between Prompting, RAG, and Fine-Tuning for a new project, I evaluate the system along two primary orthogonal axes: **Knowledge Freshness** and **Behavioral Specialization**:
> 
> 1. **Prompt Engineering:** Always the baseline starting point. Ideal for rapid prototyping, general summarization, and reasoning tasks where the model's pretrained knowledge and in-context learning are sufficient.
> 2. **RAG (Retrieval-Augmented Generation):** Mandatory whenever the application requires dynamic, real-time, or private external knowledge, auditability with source citations, or document-level access control. Fine-tuning should never be used as a factual database.
> 3. **Fine-Tuning (LoRA/SFT):** Necessary when the task requires specialized output formatting (custom DSLs, complex schemas) that prompting fails to enforce, or when distilling capabilities into smaller 8B models to eliminate bulky prompt tokens, cutting latency and costs.
> 
> In practice, we follow an evolutionary path: start with Prompt Engineering, add RAG to inject dynamic facts, and only introduce Fine-Tuning when prompt length, cost, or specialized syntax boundaries are breached."
